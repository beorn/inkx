# Overview of Silvery vs Ink for Complex Terminal UIs

Building rich **terminal UIs** for AI coding assistants (like Anthropic’s Claude Code CLI, Cursor, Aider, etc.) requires high performance, robust input handling, and advanced layout capabilities. **Silvery** is a ground-up reimplementation of the popular Ink (React CLI framework) aimed at addressing Ink’s long-standing limitations and adding new features. Ink has been widely adopted – e.g. Claude Code uses Ink ([github.com](https://github.com/vadimdemedes/ink#:~:text=Who%27s%20Using%20Ink%3F)) – but developers have noted some rough edges in performance and rendering ([www.libhunt.com](https://www.libhunt.com/posts/1476376-claude-opus-4-6#:~:text=,performance%20but%20it%27s%20nice%20overall)). Silvery introduces a redesigned architecture (two-phase rendering, pure TypeScript layout, fine-grained diffing) and expanded input/rendering features to support complex, interactive TUIs. Below, we compare Silvery and Ink in depth, and consider benefits for AI assistant CLIs, potential downsides, comparisons to non-React TUI frameworks, and the market outlook.

## Architecture and Performance Improvements

**Two-Phase Rendering & Layout** – Silvery uses a two-phase rendering pipeline so that components can know their dimensions during render via a hook (`useBoxRect`). This directly addresses a top feature request for Ink: in Ink, you cannot get an element’s size until after initial render (you must call `measureElement` in a `useEffect` after mount) ([github.com](https://github.com/vadimdemedes/ink#:~:text=Note%3A%20,after%20the%20component%20has%20rendered)). Ink’s docs note that `measureElement()` returns width/height as 0 on first render and only yields real dimensions after layout calculation ([github.com](https://github.com/vadimdemedes/ink#:~:text=Measure%20the%20dimensions%20of%20a,the%20length%20of%20its%20content)). Silvery’s two-phase approach eliminates this extra cycle, enabling layouts that depend on content size (e.g. centering text or splitting areas proportionally) to be computed in one go. This is a meaningful improvement for building complex UIs where dynamic layout feedback is needed, solving Ink’s #1 open issue (dating back to around 2016) regarding element measurement.

**Pluggable Flexbox Layout (Flexily vs Yoga)** – Silvery replaces Ink’s Yoga layout engine (which in Ink is a native C++ addon) with a pluggable system. By default it uses **Flexily**, a lightweight (~7 KB) **pure TypeScript** flexbox engine, with an option to swap in Yoga via WebAssembly if desired. This yields several benefits: being pure TS, Flexily avoids the overhead and quirks of Yoga’s WASM layer (or native module). Notably, **WASM memory can only grow, not shrink**, so long-running Yoga WASM usage tends to *monotonically increase memory usage*. In practice, Anthropics’ Ink-based Claude Code CLI suffered memory leaks and unbounded memory growth, partly due to Yoga WASM not releasing memory ([github.com](https://github.com/anthropics/claude-code/issues/4953#:~:text=Claude%20Code%20has%20a%20severe,60%20minutes%20of%20active%20use)) ([claude-world.com](https://claude-world.com/articles/claude-code-2150-release/#:~:text=Memory%20Management%20Overhaul)). Silvery’s Flexily doesn’t have this issue (it relies on JavaScript’s GC) and it also implements **layout caching** – by fingerprinting subtree styles/content, it can skip recomputing layout for unchanged subtrees. This can greatly improve performance for UIs where only small parts change. Additionally, using Flexily means **no native dependency** (no C++ compilation or node-gyp issues) and **zero init latency** (no async loading of a `.wasm` file at startup). For production CLI apps that run on many environments, eliminating native modules and asynchronous WASM loading increases stability and simplifies installation.

**Fine-Grained Dirty Tracking** – Silvery renders use a *per-node dirty tracking* system, so only nodes whose state/props changed get re-rendered, rather than diffing large text output. This dramatically speeds up interactive updates. Benchmarks on an M1 Max (Bun runtime) show a **typical update of ~1000 nodes in silvery took ~169 µs vs ~20.7 ms in Ink** – roughly **122× faster** for incremental updates. In other words, Silvery can push frequent UI updates (e.g. streaming AI assistant tokens, progress spinners, etc.) with minimal overhead, whereas Ink’s approach could struggle with high-frequency updates ([www.libhunt.com](https://www.libhunt.com/posts/1476376-claude-opus-4-6#:~:text=,performance%20but%20it%27s%20nice%20overall)). (Ink has an “incremental” mode to update only changed lines, but it still reconciles the whole tree to strings.) Silvery’s granular diffing is more akin to how web React diffing works, making updates more efficient. Cold start (initial render) in silvery is also ~1.2–1.6× faster than Ink according to its benchmarks. The trade-off is that a *full* re-render of the entire app (rare in practice) might be slower in silvery (it uses a more sophisticated pipeline vs. Ink’s simple string concat) – but in typical usage, the performance win for updates is far more impactful.

**Modern React and Multi-Layer Runtime** – Silvery is built on React 19 (versus React 18 for Ink). This means it can leverage the latest React improvements (concurrent rendering, etc., if applicable). It also architecturally combines three runtime layers: an **Elm-style reducer** for high-level state management, standard **React hooks** for component logic, and a **Zustand store** for global mutable state. This design lets developers choose the paradigm that fits best (declarative components *and* functional update loops). For example, you can manage the overall app state with an Elm-style reducer (as in Elm or Redux) – which frameworks like Bubbletea (Go) or Textual (Python) encourage – while still building the UI with React components. This hybrid approach can make complex apps more manageable without sacrificing the familiar React component model. Ink (original) is purely React and hooks, so large-scale state or cross-component coordination can be trickier without introducing your own store or messaging system. Silvery essentially builds those patterns in, which helps in complex apps (AI assistants often maintain significant state like conversation history, tool contexts, etc.).

**Rendering Pipeline Enhancements** – Silvery introduces a coordinated rendering pipeline to avoid visual tearing or flicker. Notably, it implements **synchronized (atomic) output updates**: all UI updates in a frame are computed and then written to stdout in one go. This prevents the flicker seen in Ink under certain conditions (especially in multiplexed terminals like tmux or Zellij). Ink’s approach to clearing and rewriting the screen has been criticized for causing flicker – it literally clears the entire terminal (including scrollback buffer) on each full render ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=Image%20%20%20281%2012,a%20pretty%20simple%20patch%20to)). One developer noted that Ink’s use of `ansiEscapes.clearTerminal` and line erasing can cause visible flicker, and argued for more minimal updates ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=Image%20%20%20281%2012,a%20pretty%20simple%20patch%20to)). Silvery’s dirty rendering and atomic paint solve this by only rewriting changed parts and not aggressively clearing unchanged areas, so interactive UIs (like rapidly updating “thinking...” animations or token streams) stay stable. In fact, a Hacker News commenter quipped that treating a TUI “like a small game engine” needing 16ms frames was misguided ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=of%20each%20one%2C%20as%20described,1%5D%20%20290%20https%3A%2F%2Fgithub.com%2Fvadimdemedes%2Fink%2Fblob%2Fe8)) – in practice, you can avoid flicker without clearing the screen every frame. Silvery appears to follow that advice by doing targeted updates.

## Memory and Stability Considerations

For long-running AI coding assistants, **memory leaks or bloat are serious concerns**. Silvery’s design choices prioritize stability over time:

- **No WASM Memory Leaks** – As mentioned, using a pure-TS layout (Flexily) avoids the memory creep associated with Yoga WASM. Claude Code’s team discovered multiple memory leaks in their CLI’s WASM dependencies (Yoga and Tree-sitter) and had to patch them in several updates (v2.1.47–2.1.50) ([claude-world.com](https://claude-world.com/articles/claude-code-2150-release/#:~:text=Memory%20Management%20Overhaul)). Before these fixes, users saw the Claude CLI consuming enormous RAM – reports showed it ballooning to 120+ GB and getting OOM-killed ([github.com](https://github.com/anthropics/claude-code/issues/4953#:~:text=Claude%20Code%20has%20a%20severe,60%20minutes%20of%20active%20use)). One root cause was that the Yoga WASM’s linear memory would grow with each layout but never free, exacerbated by the app’s dynamic updates. By not using WASM (or allowing opting out of it), silvery inherently dodges this class of leak. It relies on V8’s garbage collector for layout objects, which can reclaim memory, and so is better suited for *days-long* sessions typical of an always-open coding assistant.

- **No Native Addons** – Silvery has **zero native addons**, whereas Ink uses a Yoga C++ binding (unless one uses a WASM fork). This means silvery avoids issues like native module compilation on install or segfaults from C++ code. Everything is in TypeScript/JavaScript, which tends to fail more gracefully (throwing exceptions vs. crashing). For developers shipping a CLI, removing the need for platform-specific binaries is a plus – fewer installation hurdles (especially on Windows or ARM systems). Silvery is essentially “pure Node”, making it easier to bundle or run under alternative runtimes like Bun or Deno.

- **Layout Caching** – Silvery can cache layout results for subtrees that haven’t changed. In a complex UI (with dozens of components, some static, some dynamic), this prevents needless re-calculation of geometry for static parts. Ink+Yoga would recalc flex layout for the whole tree whenever anything changed, whereas silvery can short-circuit unchanged branches. This not only boosts performance but also reduces constant re-allocation of objects, contributing to lower steady-state memory usage.

- **Deterministic Cleanup with `using`** – Silvery mentions support for the new ECMAScript `using`/Disposable pattern for resource cleanup. This means components or hooks can register disposables that auto-clean on unmount (e.g. timers, event listeners). Ink’s lifecycle largely relies on React’s `useEffect` cleanup, which works but can be error-prone if not used correctly. Having `using` support suggests silvery provides a structured way to avoid leaks of event handlers or intervals – improving stability for long sessions (no slowly accumulating timers or listeners).

In short, silvery is designed to run continuously without degrading, an essential quality for a coding assistant that a developer might keep open for hours or days. Ink had to be manually tamed to achieve similar stability (as seen with Claude Code’s multiple leak fixes). By using simpler memory-managed code and caching, silvery provides more **predictable memory usage** over time.

## Input and Interactivity Features

One of the biggest differentiators of silvery is its rich input handling – an area where Ink was quite limited. Traditional Ink apps primarily handle keyboard input via `useInput` or `useStdin` hooks that give raw key events. Complex interactions (mouse, key combos, focus management) were not supported out-of-the-box. Silvery vastly expands on this:

- **Full Keyboard Protocol Support (Kitty Extended Keys)** – Silvery implements the Kitty keyboard protocol, which allows capture of key combinations beyond the typical ASCII/ANSI sequences. This means **Modifier keys like Cmd (Super/Meta), Hyper, and even key release events** can be recognized – things not possible with standard terminal input. For example, on macOS terminals that support it, `Cmd+K` or `Cmd+Shift+P` can be distinct inputs, which vanilla Ink cannot detect (it mostly gets characters and basic Ctrl combinations). For international keyboards, extended protocol support ensures keys with diacritics or non-English characters are handled properly. Essentially, silvery’s keyboard handling is closer to GUI applications or modern terminal apps (like tmux or Vim with kitty’s protocol enabled) in breadth of keys.

- **Mouse Support (SGR Mouse Protocol)** – Silvery supports mouse input natively. It uses the standard SGR mouse tracking sequences to capture clicks, scroll wheel, and even hover events (when enabled). Impressively, silvery exposes these as **DOM-like events**: e.g. you can add `onClick`, `onMouseEnter`, `onWheel` props to components, similar to React DOM events. This is entirely new compared to Ink – vanilla Ink has no direct mouse event system. For a coding assistant, mouse support can be a game-changer: e.g. ability to click on a suggested file or diff to open it, click buttons in the UI (like “Apply fix” vs typing a number), or scroll through a list with the mouse wheel. It brings terminal UI closer to a GUI experience. Competing frameworks like Textual (Python) and some Go/Rust TUIs have had mouse support; silvery evens the playing field for React-based CLIs.

- **Focus Management and Navigation** – Silvery introduces a **tree-based focus system** with focus scopes and spatial navigation. This means components can opt into focus (like form fields or interactive panes) and the framework manages which component is “active” for key input. It supports *scoped focus* (for example, all elements in a modal dialog could be a focus scope separate from the main UI), **spatial navigation** (using arrow keys to move focus in a grid or menu, akin to how you’d navigate with Tab or arrows in GUI dialogs), and **click-to-focus** (clicking on an element gives it focus). Ink’s focus handling was minimal – it has a `useFocus` hook, but that mostly just tells if the running app has terminal focus and which component is currently focused, without a comprehensive system to move focus around. Developers often had to manually manage focus state if they had multiple inputs. Silvery’s built-in system makes it feasible to have complex UIs with multiple interactive regions (for example, a sidebar tree view and a main editor area in a CLI tool) and navigate between them easily.

- **Custom Commands and Keybindings** – A standout feature for silvery is the introduction of a **Command Palette** system. It provides a `withCommands` HOC or context to define command handlers and `withKeybindings` to bind keys to those commands, plus support for a searchable palette (similar to VS Code’s command palette). This allows an application to define high-level actions (e.g. “Open File”, “Summarize Code”, “Next Suggestion”) and assign default hotkeys, which users can trigger or even search through in a pop-up. Such an architecture is far more sophisticated than anything in Ink (which would require building this manually). For an AI coding assistant CLI, this is highly beneficial: users could press a hotkey to bring up a palette of available actions rather than memorizing dozens of shortcuts or typing commands. It makes the terminal app feel more like a modern IDE. It also implies silvery likely has an **internal key event routing** – keys can be globally caught and dispatched as commands unless a focused element overrides them, etc., giving a unified way to handle shortcuts (no scattering of `useInput` in random components needed).

- **Modal Input Layers** – Silvery supports an input layer stack, meaning it can isolate input focus to a modal dialog or overlay. For example, if your assistant pops up a confirmation “[Y/N] Are you sure?” dialog or a prompt, it can temporarily grab all input, ensuring keystrokes go to that dialog (and not to the underlying UI). Once the modal closes, the previous layer regains focus. This is analogous to how GUIs handle modal dialogs. In Ink, achieving this would be manual (e.g. conditional rendering and lots of `if (modalOpen) ignore input` logic). Silvery providing a stack simplifies building multi-step interactions without input leaking to the wrong handler.

- **Hotkey Parsing with Symbols** – As a small quality-of-life touch, silvery can parse hotkey strings like `"Cmd+K"` or `"Ctrl+Alt+X"` and even understands macOS symbol notation. This means defining keybindings in config or code can be more declarative. It’s a developer convenience (and prevents mistakes in figuring out terminal escape codes for each combo).

Overall, these input improvements mean an AI coding assistant built with silvery can offer **rich, user-friendly interactions**: clickable elements, scrollable regions, definable shortcuts, and multiple interactive panels – essentially a mini-IDE in the terminal. In contrast, current Ink-based assistants are more limited. For instance, **Claude Code’s CLI lacks mouse support, custom keybindings, or robust focus management** – users mostly type commands and use arrow keys, without the refinements of a GUI. Silvery would allow such a CLI to become far more interactive and customizable, improving user experience significantly.

## Rendering and Output Capabilities

Silvery also extends what can be rendered in the terminal, adding features useful for modern terminal apps:

- **Flicker-Free Updates and Tmux/Zellij Support** – As noted, silvery batches output updates to avoid flicker. This is especially helpful in terminal multiplexers or when outputting over remote sessions where partial draws can be noticeable. Ink had an open issue about flickering (with suggestions to use the alternate screen buffer to mitigate it) ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=expected%20to%20cause%20tearing%2Fjank%20,2%5D%20https%3A%2F%2Fgithub.com%2Fvadimdemedes%2Fink%2Fissues%2F359)). Silvery’s approach of atomic painting ensures that even rapid updates (e.g. token-by-token stream from an AI) don’t cause the UI to momentarily blank or tear. This makes the UI feel much smoother, akin to desktop apps. No more seeing the entire screen clear and redraw, which was an Ink quirk (clearing scrollback each render) ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=Image%20%20%20281%2012,a%20pretty%20simple%20patch%20to)). Developers have pointed out that many TUIs (htop, vim, etc.) manage to update specific regions without flicker ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=expected%20to%20cause%20tearing%2Fjank%20,2%5D%20https%3A%2F%2Fgithub.com%2Fvadimdemedes%2Fink%2Fissues%2F359)); silvery aligns with these best practices by updating only what’s needed.

- **“Scrollback Mode”** – Silvery introduces a concept called *scrollback mode*, wherein output that is “done” can be **committed to the terminal’s scrollback**. This is very interesting: it implies that parts of the UI can be released from the live updating screen and become regular scrollback text. For example, suppose the assistant had a long chat transcript; older messages could be “finalized” into the scrollback buffer, improving performance and memory (they are no longer part of the active React tree, but remain visible above). New output would appear below. Essentially, it can freeze certain completed UI sections as normal terminal text. This mode could also allow the program to terminate but leave content in scrollback for the user to review (whereas normally, if you use an alternate screen, all content disappears on exit). Ink doesn’t have an equivalent feature – it either uses normal buffer or alt screen for everything. Scrollback mode is a nuanced capability that, if used wisely, could give users the best of both worlds: interactive interface *and* persistent log of results.

- **Adaptive Rendering** – Silvery can detect if it’s running in a non-interactive context (non-TTY or unsupported terminal) and degrade gracefully. For example, if the assistant CLI is run in a dumb terminal or piped to a file, silvery can output simple text (without control codes or dynamic updating). This ensures compatibility in automation scenarios or when capturing output. Ink-based CLIs, if not explicitly handled, might output raw control sequences or just not run. Adaptive rendering broadens the usability of the CLI. An AI assistant could thus provide a basic output when used in a script, whereas with a full TTY it provides the rich UI.

- **Inline Images via Kitty Graphics Protocol** – Silvery supports displaying images in the terminal using the Kitty graphics protocol. This is an advanced feature allowing pixel graphics to be rendered (supported in Kitty, iTerm2, and some other modern terminals). For a coding assistant, this could mean showing an image (e.g. a chart, screenshot, or diagram generated by an AI) right in the console. While perhaps an edge-case for coding tools, it opens possibilities – for example, “explain this code diagram” could display a rendered diagram. This goes beyond Ink’s capabilities; Ink was limited to text (and colors) only. Silvery’s built-in support means developers can drop in an `<Image src="..."/>` (hypothetically) and have it appear, rather than manually managing escape sequences.

- **Hyperlinks (OSC 8)** – Silvery provides a `Link` component or similar, which uses the OSC 8 terminal hyperlink protocol. This allows embedding clickable hyperlinks in terminal text (many terminals turn these into click-to-open links). An assistant could output documentation links, issue tracker URLs, or any references as clickable text. This was not directly provided by Ink (though one could embed the escape codes manually). Having a built-in component makes it straightforward and less error-prone. It enhances the user experience – e.g. “View full docs 【here】” where “here” is clickable in supporting terminals.

- **Alternate Rendering Targets (Canvas2D, DOM)** – Impressively, silvery is designed such that the same React component tree could potentially render to targets other than the terminal. The mention of Canvas 2D and DOM outputs suggests the library can run in a headless mode to produce a graphical representation or even mount to a browser DOM. This could be used for generating screenshots of the TUI, or perhaps for testing, or a web preview. For instance, one could imagine a web-based demo of the CLI where the UI is rendered in the browser with DOM elements styled to look like a terminal. The fact that silvery components aren’t tied strictly to stdout means more flexibility. Ink was purely terminal-bound (aside from its testing library which rendered to a virtual output). Silvery’s rendering abstraction could facilitate things like a built-in **screenshot utility** (`bufferToHTML()`), which they mention. Indeed, silvery can convert the current UI buffer to an HTML snippet/image, which is great for documentation or debugging – you can programmatically take a “snapshot” of the TUI at any moment. This feature shows the thoroughness of silvery’s design; it acknowledges use-cases like generating bug report visuals or embedding the TUI in a webpage for marketing.

In summary, silvery’s rendering upgrades ensure that complex UIs look and behave better in the terminal (no flicker, optional images/links), and even allow the UI to transcend the terminal if needed. An AI coding assistant using silvery could, for example, output a clickable link for each piece of code documentation it finds, or even show a small image (maybe a Git diff heatmap or dependency graph). These polish features help bridge the gap between text-based interfaces and modern expectations.

## Testing and Reliability

Given the complexity of interactive TUIs, testing is important. Silvery introduces tools to help verify UI output:

- **`withDiagnostics` Mode** – Silvery can run in a special diagnostics/testing mode where it automatically compares incremental renders to full renders to ensure its diffing algorithm is correct. This catches any inconsistencies in the optimized rendering (a smart way to verify that the dirty-tracking doesn’t produce glitches). For developers, this means you can be confident the performance optimizations aren’t skipping something they shouldn’t. Ink (original) relies on the React reconciler’s guarantees, but since silvery implements more custom rendering logic, this diagnostic feature is critical. It’s a sign that silvery is built with **robustness in mind**, suitable for production.

- **Playwright-Style Locators** – Silvery offers a testing API with **locator queries** such as `getByTestId`, `getByText`, etc., similar to Playwright or Testing Library in the web world. This means you can write tests that mount your TUI components (probably using a headless mode or a virtual terminal buffer) and then query for elements and assert their content or state. For example, you could simulate a key press and then assert that `getByText("Error: File not found")` appears on the screen, or that a certain component received focus. Ink’s testing library (ink-testing-library) was limited to snapshotting the output text or querying by text content. Silvery’s approach allows more structurally aware tests, which is important as UIs become more interactive (text output alone might not tell you which element is focused or what command palette options exist unless you parse raw text). By having a notion of element tree in tests, one can simulate user interactions more effectively. In effect, silvery treats the TUI like a real UI for testing purposes, which is vital for complex apps that need to be reliable.

These testing improvements mean developers building on silvery can adopt TDD or at least write comprehensive automated tests for their CLI’s behavior, catching regressions in UI logic. This is especially relevant for AI assistants – one could write tests for certain prompts and ensure the assistant’s UI shows the right response or that the “busy” spinner appears while waiting, etc. As these assistants integrate more features, tests ensure stability.

## Benefits of Silvery for AI Coding Assistants

Given the above, an AI coding assistant CLI stands to gain significantly by using silvery over Ink:

- **Better Performance & Responsiveness:** The assistant can update its UI (e.g. streaming chat replies, file diffs, progress bars) smoothly without lag or flicker. The 100× faster update performance translates to a snappier interface, which is crucial when the assistant is outputting tokens rapidly or updating multiple components at once. Users will notice fewer visual artifacts and more real-time feedback, which improves the UX of interacting with the AI. One developer who used Ink noted “rough edges in rendering performance” ([www.libhunt.com](https://www.libhunt.com/posts/1476376-claude-opus-4-6#:~:text=,performance%20but%20it%27s%20nice%20overall)); silvery directly tackles this, so even as the assistant’s output grows large or updates frequently, it remains responsive.

- **Rich, Intuitive UI Interactions:** Silvery would let a coding assistant move beyond a basic chat prompt interface toward a full-fledged IDE-like experience in the terminal. For example, the assistant could present editable text inputs, clickable suggestions, dropdown menus for selecting refactoring options, etc. A user could click on an error message to jump to that file location, or press a custom hotkey (say, `Ctrl+N`) to create a new file via the assistant. Custom **keybindings** mean power-users can navigate and trigger actions quickly (and possibly even rebind keys to their liking in config). Focus management means the assistant can have multiple panes (perhaps one showing conversation, another showing file changes) and the user can switch focus with Tab or clicks – this multi-pane interaction is something current CLI assistants don’t handle well. Essentially, silvery can make a terminal-based coding assistant feel more like using a text editor (with menus, dialogs, and mouse support) rather than a simple REPL. This lowers the learning curve and increases efficiency for users.

- **Improved Stability for Long Sessions:** AI coding assistants are often used for hours continuously as part of a coding workflow. Memory leaks or crashes are thus highly disruptive. By adopting silvery, an assistant like Claude Code could avoid the major memory issues that plagued earlier versions. For instance, Claude Code had an incident where a memory leak caused it to crash every 30-60 minutes ([github.com](https://github.com/anthropics/claude-code/issues/4953#:~:text=Claude%20Code%20has%20a%20severe,60%20minutes%20of%20active%20use)). Silvery’s memory-safe approach (no growing WASM heap, proper disposal) would help ensure the assistant can run indefinitely without gobbling memory. No need for frequent restarts or workarounds. This reliability is crucial for user trust – one Hacker News commenter discussing coding agents mentioned that current tools have “glitches and paper cuts” but over time they must improve ([news.ycombinator.com](https://news.ycombinator.com/item?id=46844822#:~:text=part,a%20rigid%20proprietary%20client%20app)). Silvery can eliminate an entire class of such glitches (e.g. losing context due to an OOM crash).

- **Feature Parity with Modern Apps:** Many users expect their tools to be customizable and feature-rich. With silvery, an AI CLI could offer a **palette of commands** (making discovery of functionality easier – the user can press a key to see what the assistant can do), and even incorporate GUI-like elements (imagine an inline image of a UML diagram the AI produced, or simply the ability to scroll through long outputs with the mouse). These features can set the assistant apart from competitors. For instance, if Aider (open-source assistant) adopts silvery and offers a clickable UI or images, it could provide a better UX than a more static competitor. For teams building such assistants, these capabilities might become selling points.

- **Easier Development & Maintenance:** From the developer’s perspective, silvery’s improvements can speed up development. The ability to measure layout in-render, the built-in focus and input handling, and the testing facilities all reduce the amount of “boilerplate” or hacky solutions the developers need to write. They can rely on the framework for those pieces and focus on the core logic of the AI assistant. This means faster iteration and fewer bugs. Silvery’s React 19 base also means devs can use the latest React patterns and possibly integrate with React DevTools for debugging (Ink supports React DevTools as well ([github.com](https://github.com/vadimdemedes/ink#:~:text=Using%20React%20Devtools)), and one assumes silvery does too). Overall, adopting silvery could accelerate the development of new features in the assistant (for example, adding a new popup dialog is trivial with the modal input layer, whereas in Ink it would require careful manual input handling).

In short, silvery equips AI coding assistants with a more **professional-grade TUI framework**, which translates to a smoother user experience, more capabilities, and potentially a competitive edge in a growing field of AI developer tools.

## Risks and Downsides of Silvery vs Ink

Despite the advantages, there are considerations and potential downsides in choosing silvery, especially since Ink has a **mature ecosystem**:

- **Ecosystem Maturity:** Ink has been around for years, accumulating ~35k GitHub stars and many users. It’s battle-tested in lots of CLIs (from small tools to big ones like GitHub’s Copilot CLI and Anthropic’s Claude Code) ([github.com](https://github.com/vadimdemedes/ink#:~:text=Who%27s%20Using%20Ink%3F)). Silvery is new (as of late 2026) and not yet widely adopted. This means **fewer community resources** – e.g. fewer third-party components or examples to draw on, fewer discussions on Stack Overflow, etc. Ink has a number of ready-made components (like `ink-text-input`, `ink-select-input` for menus, spinners, etc.) and community packages. Silvery, being mostly API-compatible but not completely identical, may not instantly have equivalents for all those. Adopting silvery might require porting some Ink components or writing new ones. If an issue arises in silvery, the community might be smaller to help debug it compared to Ink’s community.

- **Stability and Bugs:** While silvery is designed for stability, it’s still a new implementation and could have undiscovered bugs. Ink’s core has been refined by real-world use and many bug reports over time. Silvery’s ambitious features (e.g. new input protocols, custom reconciler) add complexity that might not have been exercised in all edge cases yet. Early adopters might encounter issues that need fixes. Silvery does have diagnostic tools to catch rendering issues, but it may take time to reach the same level of confidence that “this just works” that a mature project has. Essentially, there’s a *risk in being an early adopter* – one should be prepared to work with the silvery maintainers or even contribute fixes if something goes wrong.

- **Breaking Changes and Compatibility:** Silvery runs on React 19. Apps using Ink (React 18) might need to upgrade React version to use silvery, which is generally fine but could introduce incompatibilities if other parts of the app ecosystem aren’t ready for React 19. Also, if an existing CLI is built on Ink, migrating to silvery would involve some changes. The core concepts (JSX components, <Text>, <Box>, etc.) are similar, but under the hood differences (e.g. Yoga styles vs Flexily) might cause slight layout differences. There might also be new APIs to learn (for commands, focus, etc.) – though optional, they are additional surface area. If a team’s developers are very used to Ink’s patterns, there could be a learning curve adopting silvery’s advanced features.

- **Performance Trade-offs:** Silvery’s fine-grained approach yields big benefits for interactive UIs, but as mentioned, full re-renders of the entire UI might be slower than Ink. If an application frequently mounts/unmounts large portions of the component tree or completely re-renders everything, silvery’s overhead might show. Ink’s simpler diff-to-string approach can be very fast for static or batched output (for example, printing a large static table once). However, in practice AI assistants update incrementally, so this is a minor concern. Additionally, silvery’s reliance on an in-process JS layout engine means if someone did choose to use Yoga via WASM, they’d reintroduce some overhead. But using Yoga in silvery is optional – presumably only if one needs exact parity with web Yoga layout quirks. For most, Flexily should be fine. It’s worth noting that Flexily is new and its flexbox implementation might have subtle differences or missing features compared to Facebook’s Yoga (which has years of refinement and edge-case handling for CSS layout). If a layout bug exists in Flexily, it could affect the UI until fixed. By contrast, Yoga is quite stable (though it had memory issues in WASM form, its layout logic is well-tested by React Native et al.). So there’s a slight risk in using a new layout engine; one might encounter a scenario where a flex container doesn’t behave as expected.

- **Library Support and Tooling:** Silvery being new might lag in integrations with tooling. For example, the Ink Testing Library and Ink DevTools integration are known quantities – silvery has its own testing utilities, but those need to be learned and might not yet have extensive documentation or community knowledge. Similarly, if your CLI uses Ink-specific patterns or context (like Ink’s `useStdout` or `useApp`), you’d need to see how silvery handles those (likely similarly, but not guaranteed). Essentially, adopting silvery means being on the cutting edge – one should be comfortable reading its documentation/source to make full use of it, whereas Ink has many blog posts, tutorials ([blog.logrocket.com](https://blog.logrocket.com/using-ink-ui-react-build-interactive-custom-clis/#:~:text=Using%20Ink%20UI%20with%20React,I%20enjoy%20learning%20about)), and Q&A that could help.

In summary, the **risk vs reward** analysis: Silvery offers compelling improvements, but a team must consider the maturity gap. For a new project aiming to push the envelope of terminal UI, silvery might be worth the risk. For an existing stable project, maintainers might wait for silvery to prove itself or reach a 1.0 stability milestone. However, given that many of silvery’s features directly address pain points that real apps (like Claude Code) have hit, the impetus to switch could be strong if those pain points are causing user frustration.

## Comparison to Non-React TUI Frameworks

Silvery not only leapfrogs Ink, but also narrows the gap between Node.js-based TUIs and those built with other languages/frameworks like **Textual (Python)**, **Ratatui (Rust)**, or **Bubbletea (Go)**. These non-React frameworks have been popular for more advanced TUI applications, each with their own paradigm:

- **Bubbletea (Go)** – uses the Elm update-model-view architecture and supports pretty advanced TUIs (keyboard, mouse events, etc.). It’s known for performance and a robust state management model, at the cost of writing in Go and not having a React-like component abstraction. Silvery, by incorporating an Elm-style reducer layer and focusing on performance, essentially brings the architectural robustness of Bubbletea into the JS/TS world. It provides a message-passing model (commands and keybindings) akin to Bubbletea’s message system, but still lets you build UI with declarative components if you want. Moreover, silvery’s new input capabilities (mouse, extended keys) put it on par with Bubbletea’s – which also supports mouse events and has an ecosystem (Charmbracelet libs) for things like text inputs, etc. One could say silvery lets JS developers achieve what Bubbletea offers Go developers: a powerful, interactive TUI, but using React skills. Performance-wise, with dirty tracking and efficient diffing, silvery on modern JS runtimes likely approaches Go speeds for typical UI interactions (and certainly enough for 60fps-equivalent updates, given 169µs update times). In short, **silvery bridges the gap** by offering the performance and features traditionally associated with Go TUIs, within a React framework.

- **Textual (Python)** – Textual is quite sophisticated: it has a DOM-like widget tree, CSS styling, and even the ability to run as a web app. It supports mouse, focus, etc., and is often praised for bringing “modern GUI paradigms” to the terminal. Silvery is analogous in ambition. It too has a component tree and even multiple render targets (similar to how Textual can render to the web). Silvery’s approach to styling isn’t using CSS (styles are likely set via props in React style), but it offers a lot of what Textual does: layout, animations (indirectly via React transitions potentially), etc. One area Textual shines is theming and using CSS selectors to style widgets; silvery doesn’t mention an equivalent, relying on inline styling via props. However, since silvery is React, one could compose styled components or use context for theming. Where silvery clearly catches up is **input and widget complexity** – e.g., Textual has a concept of focus and actions, which silvery now also has with its focus and command system. A Python developer might choose Textual for a complex TUI, but a Node developer can now choose silvery and achieve similar complexity. It’s worth noting Textual’s performance can be a concern (Python overhead for many updates), whereas Node/Bun with silvery might actually be more performant in some cases. Both aim for flicker-free, rich UIs. Silvery having features like inline images and hyperlinks also shows parity with Textual, which recently added image support and already had hyperlink support. Essentially, silvery is **JS’s answer to Textual**, giving similar capabilities but with React syntax.

- **Ratatui / tui-rs (Rust)** – These are low-level but efficient TUI libraries in Rust that let you draw UIs (usually with an immediate mode pattern or a retained widget tree) and handle input via Rust’s event system. They excel in performance and control. However, they lack the high-level declarative structure that React provides and require Rust development. Silvery likely won’t beat a tuned Rust app in raw performance, but it eliminates the need for most Node developers to reach for Rust just to get a smooth TUI. By solving the major performance issues of Ink, silvery keeps Node in the running for these use cases. And with far less code complexity: e.g., building a scrollable list with mouse support in Rust TUI might involve manual tracking of scroll offsets and drawing routines, whereas in silvery you could simply use a `<Box overflow="scroll">` and get that behavior, or similar. So developer productivity in silvery is higher. Ratatui doesn’t have built-in command palettes or focus management at a high level – you implement your own state machine – so silvery provides more out-of-the-box functionality. 

In general, **silvery closes the functionality gap** between React/JS TUIs and the more “native” TUI frameworks. A Hacker News user discussing CLI tooling once pointed out alternatives in Go, Python, Rust for CLI UIs ([news.ycombinator.com](https://news.ycombinator.com/item?id=35864458#:~:text=For%20Golang%20there%20is%20Bubbletea,line%20apps)) – implying that if you wanted a really polished CLI, you might opt out of Node/Ink and use those. With silvery, that calculus changes: one can stick with the Node/TypeScript ecosystem and still get a top-tier TUI. This is particularly important if the rest of your application logic or AI integration is in Node/TS (which is common for tools interfacing with Node packages, AWS SDKs, etc.). Silvery allows you to have both: the convenience of one language stack and the advanced UI features.

That said, frameworks like Textual and Bubbletea have a head start and their own ecosystems (e.g., Textual has Textual IDE, Bubbletea has Charm’s many UI components). Silvery will compete by leveraging the huge React ecosystem – web developers who know React can transfer skills to building CLIs. The learning curve for silvery is lower if you know React, compared to learning a whole new framework/language. This could potentially draw people who wouldn’t have built a TUI at all before into doing so with silvery, expanding the pool of TUI applications.

## Market Opportunity for Silvery

Silvery enters the scene at a time when **terminal-based AI assistants and complex CLIs are on the rise**. The success of tools like Claude Code, GitHub Copilot CLI, Google’s Gemini CLI, etc., shows a demand for richer command-line experiences for developers ([github.com](https://github.com/vadimdemedes/ink#:~:text=Who%27s%20Using%20Ink%3F)) ([www.libhunt.com](https://www.libhunt.com/compare-ink-vs-bubbletea#:~:text=,CLI%20tools%20like%20Claude%20code)). These are essentially mini IDEs or chatbot interfaces running in the terminal, and users expect them to be engaging and efficient. Silvery is well-poised to become the framework of choice for such projects due to several factors:

- **Addressing a Real Need:** The creators of silvery clearly built it in response to concrete issues encountered with Ink in production (performance bottlenecks, memory leaks, lack of advanced input). Claude Code’s team, for example, spent effort fixing Ink-related issues and still lacked features like mouse support. There’s likely an appetite in those teams for a better solution. If silvery proves stable, we might see companies like Anthropic, Google, or open-source projects adopt it in upcoming versions to improve their CLI tools. The **value proposition** is strong: significantly better UX and performance with presumably manageable migration effort (since it’s React-based). This means silvery could rapidly gain traction in the niche of AI CLI tools. Even beyond AI, any interactive CLI (cloud DevOps tools, dashboards, etc.) would benefit from silvery’s features.

- **Leveraging React Familiarity:** There are millions of JavaScript/TypeScript developers who know React. Ink already tapped into this talent pool by making CLI dev feel like writing a React app. Silvery continues this approach, meaning its potential contributor and user base is large. The barrier to entry is low for new devs: if you can write a React UI, you can create a TUI with silvery. This broad appeal can drive adoption, especially as it’s open-source. Companies might be more willing to build complex internal tools if they can use common web tech rather than specialized libraries in other languages. As more developers experiment with building their own AI helpers or custom CLIs (which is increasingly common in the dev community), silvery could become a go-to choice. We’ve already seen questions on forums like HN asking how tools like Claude Code are built ([www.libhunt.com](https://www.libhunt.com/compare-ink-vs-bubbletea#:~:text=,CLI%20tools%20like%20Claude%20code)) – indicating interest. If silvery is well-publicized, developers trying to build “Claude but custom” will likely try silvery.

- **Competitive Edge in Features:** Silvery’s feature set can spark new categories of terminal apps. Think of an AI assistant that can incorporate a mini file explorer tree, or a testing dashboard that shows live charts in the terminal (via images or drawing on a Canvas target). These were hard or impossible with previous frameworks. Silvery opens those possibilities, so we may see *innovative TUI designs* that weren’t attempted before. Being the enabler of those, silvery can capture mindshare as a cutting-edge toolkit. Early adopters in open source might showcase what silvery can do, attracting more users. If one project demonstrates a very slick terminal UI (thanks to silvery), others will follow to not be left behind.

- **Community and Ecosystem Growth:** As silvery gains users, we can expect an ecosystem to form around it – much like Ink has plugins and Textual has a community. If the maintainers actively support the project, fix issues, and engage with early adopters, it could quickly mature. Since it’s open-source (the GitHub is `beorn/silvery`), community contributions could accelerate its development. There’s a window of opportunity now: if Silvery is the first to implement these solutions in Node land, it can become the de-facto choice before others catch up. (Ink itself might try to update – but a ground-up redesign like silvery indicates Ink’s author hadn’t implemented some of these in years, so silvery has the first-mover advantage for the “next-gen” Ink.)

- **Integration with AI Ecosystem:** Given its focus on AI assistant use cases, silvery might integrate well with other AI tooling. For instance, if Anthropics or others contribute, they could tailor it to AI agent needs (like better support for streaming text with tokens highlighted, etc.). If silvery becomes known as the “framework that powers Claude Code 3.0” (hypothetically), it will gain credibility and likely a surge in interest from developers of similar tools. The AI boom means there’s a *market trend of building custom agents* (for personal use, enterprise, etc.). Many of those could be CLI-based (for accessibility and simplicity). Silvery stands to capture this trend, becoming to AI CLI apps what frameworks like React Native are to mobile apps – a standard foundation.

Of course, success isn’t guaranteed. Silvery will need to prove itself in real-world apps and build a community. But the timing is favorable: developers are currently pushing the envelope of what terminal apps can do (in part due to the AI agent influence). There’s a convergence where **terminals are becoming more capable** (e.g. kitty’s graphics, new protocols) and **user expectations are rising** (CLI tools shouldn’t be clunky). Silvery is arriving right at this convergence, offering an open-source solution that encapsulates these new capabilities.

In summary, the market opportunity for silvery is significant in the developer tools space. If it can deliver on its promises of performance and features, it has the potential to *supplant Ink* for complex TUIs and perhaps draw users away from non-JS TUI frameworks who prefer to stick with TypeScript. With the growth of AI coding assistants and similar interactive CLIs, silvery could become a key enabler – powering the next generation of intelligent, user-friendly terminal applications.
