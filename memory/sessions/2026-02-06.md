
## Session 227d13d3 (12:14)

- Decisions made and why
  - Add suppress: true to patchConsole in view.ts (patchConsole(console, { capture: true, suppress: true })) to ensure console output is captured for the UI and not dumped to the terminal. Reason: -vv debug logs were flooding the terminal and breaking the TUI.
  - Add suppress: true to fallback patch in tui.tsx as well, for the same reason (to cover cases where patchConsole isn’t provided).
  - Fix toast UX: Change useLogToast in board-bottom-bar.tsx to fire only once (one-shot) when the log total becomes non-zero, not on every update. Reason: verbose logs produced hundreds/thousands of toasts, obscuring the UI.
  - Keep progress rendering separate: Acknowledge that progress UI uses direct stdout writes and is unaffected by console suppression; suppression targets console.* logs, not process.stdout paths.

- Bugs found and root causes
  - Console flood in TTY: writeLog() uses console.debug and patchConsole with capture only; suppress did not apply, so logs still reached the terminal.
  - Toast flood: useLogToast fired on every consoleStats.total update, so high-frequency log streams produced many toasts covering the UI.
  - Import alias confusion (pre-refactor): view.ts had two imports aliasing the same createLogger function, indicating a rename/refactor drift that didn’t change behavior.

- Approaches that failed and why
  - Relying solely on capture without suppress: capture alone did not stop console.* from writing to the terminal, so the TUI UI remained compromised.
  - Debouncing toasts without changing trigger logic: Debounce helped some UI components but not when the underlying signal (consoleStats.total) updates extremely rapidly; users still saw floods.
  - Assuming progress UI would be affected by console suppression: progress renders via process.stdout, not console.*, so suppression needed to be scoped to console.*.

- Architectural patterns or conventions discovered
  - Console patching pattern: using patchConsole with capture and suppress to route console messages into a Console component within the UI, keeping the terminal clean.
  - Clear separation of concerns: console logs (captured and replayed in UI) vs. direct stdout progress rendering (unaffected by console patching).
  - UI feedback best practices under high-frequency logs: prefer one-shot notifications or throttled updates rather than per-event to avoid UI clutter.

- Warnings for future sessions
  - Verify patchConsole usage comprehensively: ensure suppress is set where needed; default behaviors can be surprising.
  - Be cautious with log-driven UI: high-frequency logs can overwhelm toasts; implement one-shot or proper throttling for log-related UI notifications.
  - If enabling verbose logs, validate both TUI stability and user experience (avoid masking real UI state with flood of messages).
  - Understand the boundary between console-based logs and progress rendering to avoid unintended suppression effects on non-console outputs.
  - Submodule and repo state: monitor in-progress merges (AUTO_MERGE) as they can affect debugging context.
