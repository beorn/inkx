  - Assuming progress UI would be affected by console suppression: progress renders via process.stdout, not console.*, so suppression needed to be scoped to console.*.

- Architectural patterns or conventions discovered
  - Console patching pattern: using patchConsole with capture and suppress to route console messages into a Console component within the UI, keeping the terminal clean.
  - Clear separation of concerns: console logs (captured and replayed in UI) vs. direct stdout progress rendering (unaffected by console patching).
  - UI feedback best practices under high-frequency logs: prefer one-shot notifications or throttled updates rather than per-event to avoid UI clutter.

- Warnings for future sessions

  - Be cautious with log-driven UI: high-frequency logs can overwhelm toasts; implement one-shot or proper throttling for log-related UI notifications.
  - If enabling verbose logs, validate both TUI stability and user experience (avoid masking real UI state with flood of messages).
  - Understand the boundary between console-based logs and progress rendering to avoid unintended suppression effects on non-console outputs.
