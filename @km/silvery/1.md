# [x] Interactive node signals — per-node reactive state (hovered, armed, selected, focused) on ag nodes @km/silvery #feature #P2

Per-node reactive signals on ag nodes for interactive state. Like CSS pseudo-classes (:hover, :active, :focus, ::selection) but as alien-signals.

## Signals per ag node

- node.hovered — pointer is over this node (enter/leave)
- node.armed — pointer-down, will receive click if released here (:active)
- node.selected — in the selection set
- node.focused — has keyboard focus
- node.dropTarget — something dragging over this node
- node.dragging — this node is being dragged

## Who writes

- Pointer system: hovered (enter/leave), armed (down/up + proximity)
- Selection store: selected (diff old vs new, write only changed nodes)
- Focus manager: focused
- Drag system: dragging, dropTarget

## Why

- No global set membership checks (O(1) signal read, not sel.node.ids.has(id))
- Maximum granularity (only affected nodes re-render)
- Unified interface (all interactive state works the same)
- Default theme styling possible (silvery auto-applies hover highlight, selection highlight, focus ring)
- Cursor move = 2 signal writes (old node false, new node true), not full set recomputation

## Scope

Phase 1 (selection): sel.node.select() writes node.selected directly. Proves the pattern.
Phase 2 (hover/armed): pointer system writes node.hovered and node.armed.
Phase 3 (theme): silvery default theme reads node signals for auto-styling.

## Relationship to selection

Selection store is the first consumer. sel.node.select([id]) internally diffs and writes node.selected on changed nodes. Other consumers (rendering, a11y) read node.selected — no intermediate computation.

Virtualization: if a node unmounts, its signal disappears. Selection store keeps the ID in its internal set. When the node remounts, the store writes selected=true on the new signal.
