# [x] Concurrent FS/DB edits may lose changes @km/_orphan #bug #P3

## Description

New bidirectional chaos tests reveal that concurrent edits from filesystem and database sides may not all propagate correctly.

## Symptoms

1. **Rapid FS edits lost**: When multiple rapid FS edits occur (10 edits, 20ms apart), the final DB state may not reflect the last edit
2. **Multi-file race condition**: When editing file1 via DB and file2 via FS simultaneously, file2's FS changes may not be synced

## Reproduction

```bash
bun test packages/km-storage/tests/watch/chaos/concurrent.test.ts
```

Failing tests:

- "many rapid FS edits are coalesced" - expects "Edit 10", gets "Task"
- "concurrent edits to different files are independent" - Task 2 stays "todo" instead of "done"

## Investigation Needed

- May be test timing issues (debounce not settled)
- May be real sync bugs (events being dropped)
- Need to add debug logging to understand event flow
