## Venture #11 — ACP-to-Matrix gateway (the standout, added in second pass)

The first 22+ entry in the file. Added after revisiting the table with the architectural fork "build N direct adapters vs use Matrix as the chat substrate." The latter wins decisively because the matrix.org bridge ecosystem (~25 channels, 8 years of bug-fixes) does the work for us.

### Shape

Channel-agnostic gateway with Matrix as the default chat substrate + direct adapters for non-chat surfaces (REST/voice/webhook) and premium chat (Slack/Discord direct, where channel-specific UX matters).

```
[ACP client]
    ↓ ACP / JSON-RPC
[acp-gateway]
    ├─ chat surfaces → Matrix substrate → {Slack, Discord, Telegram, WhatsApp,
    │                                       Signal, iMessage, IRC, SMS, Email, ...}
    │                                       (via existing matrix-appservice-* bridges)
    ├─ non-chat surfaces → direct adapters (REST + SSE, webhooks, voice, webchat)
    └─ premium chat → direct adapters (Slack-direct for blocks, Discord-direct for threads)
```

### Why this collapses 4-5 entries in the table

- **#10 Multi-surface output** — every Matrix client = a surface, free.
- **#7 Cross-machine federation** — Matrix federation IS our federation.
- **#9 Provenance** — Matrix events are cryptographically signed; chain is built-in.
- **#4 Tool governance** (partial) — Matrix power levels gate who can issue tool calls.
- **§4.4 Cross-machine swarms** — Matrix rooms are inherently multi-participant.

### Phased rollout

| Phase | Scope | ETA |
|---|---|---|
| v1 | ACP↔Matrix only — gateway + session-room mapping + message translation. Ships with Element/Cinny/Nheko as clients + every Matrix bridge transparently. | 2 weeks |
| v2 | Direct Slack adapter as premium tier (interactive blocks, slash commands) | +3 weeks |
| v3 | Direct Discord adapter (threads, voice channels, embeds) | +3 weeks |
| v4 | REST + webhook + voice as separate plugins, demand-driven | TBD |

Each phase ships independent value; v1 alone covers ~90% of the chat-channel TAM via Matrix bridges.

### npm names reserved (2026-04-27)

`acp-gateway` (canonical), `acpmatrix` (Matrix-bridge variant), `acpservice`, `acpchannel`, `@beorno/acpgateway`, `@beorno/acpsv` (collisions held under scope).

### Why it scores 22

- **Real (5)**: Matrix is mature (60M+ users, govt+enterprise, Element-funded); ACP is shipping; bridge pattern proven; each existing matrix-appservice-* validates the architecture.
- **Win (4)**: silvercode has the ACP investment (`apps/silvercode/packages/agent-harness/`); matrix-bot-sdk is solid; nobody else has both interests.
- **Worth (5)**: distribution channel = entire Matrix ecosystem + every chat bridge. Strategic centerpiece for ACP-as-proxy.
- **Wedge (4)**: ~3-5K LOC TypeScript, MVP in 2 weeks, foundation for all later phases.
- **Moat (4)**: first-mover in `matrix-appservice-acp` namespace; network effects; Anthropic/OpenAI/Cursor structurally won't build it.

### Real risks (not deal-breakers)

- **Matrix complexity** — Olm/Megolm encryption + Synapse heaviness. Mitigation: Dendrite/Conduit homeservers; E2E optional in v1.
- **Self-host friction** — "you need a homeserver" kills adoption. Mitigation: hosted Matrix as the SKU (Element's playbook); OSS gateway + paid hosting.
- **ACP schema churn** — protocol is young. Mitigation: gateway IS the version-translation layer (acp-proxy.md §4.5).
- **Education tax** — Matrix mindshare is chat-shaped, not agent-shaped. Mitigation: own the "Matrix for agents" category.

### Spec authorship — the moat that bumps Moat 4 → 5

Building the gateway is also how we plant the flag for **`org.acp.*` event types as the standard agent-vocabulary on chat substrates** (Matrix initially; potentially XMPP, Slack-via-extension, anywhere chat lives). This matters because:

- Chat protocols (Matrix, XMPP, IRC, Slack) were not designed for agents. The "agent in a chat room" use case is genuinely new and there's no incumbent vocabulary for streaming responses, tool calls, content-block typing, plan-vs-reply phases.
- ACP already has these primitives. Custom event types like `org.acp.tool.call`, `org.acp.content.block.diff`, `org.acp.plan.step` are the natural Matrix-shaped expression.
- **Whoever ships well-designed event types first becomes the standard author** — same pattern as Anthropic with MCP for tool calls. The reference implementation IS the spec.
- Matrix has a formal MSC (Matrix Spec Change) process. Submitting our event types as MSCs gives them governance legitimacy.
- Once `org.acp.*` is in the Matrix spec, every other ACP host (Zed, future agent vendors) adopts it because there's no second well-designed option. **Spec authorship is sticky in a way product features aren't.**

The competitive risk: Anthropic might extend MCP into this space, OpenAI might propose `oai-chat-events`, Google might assert something with Gemini. **Window is open *now* and closes fast** — once one of them ships their version, ours is "yet another competing standard" rather than "the obvious one."

The initial event-type sketch lives at [`hub/silvercode/future/ai-terminal/acp-event-spec.md`](../silvercode/future/ai-terminal/acp-event-spec.md). It captures the v0 vocabulary that the gateway would emit and serves as the seed for the eventual MSC submission.

### Why Moat goes from 4 to 5

A typical venture's moat is product-shaped (network effects, data flywheel, switching cost). This venture's moat has all of those *plus* spec authorship — which is structurally different. Specs are sticky over decades (HTTP, IRC, MIME, OAuth, MCP). Once the agent ecosystem standardizes on `org.acp.*` events, the gateway authoring them is the canonical reference, and replacing it requires re-standardization. That's **a 10-year moat, not a 3-year moat**, hence Moat=5.

This bumps the venture's total to **23/25** and reframes it from "a strong product" to "a candidate generational company": the gateway is the SaaS, the spec is the standard, and one company holds both. *That's* the prize-shaped venture the original brainstorm was missing.

## Venture #12 — km chat rooms as ACP-session JSONL

Pairs with #11. Where #11 ships the gateway + spec, #12 ships the canonical *storage* for the same vocabulary.

### Shape

ACP defines session IDs as a wire concept but does not standardize a session format. Each agent persists its own way (claude-code's `.jsonl` per session, codex-acp's CLI store, etc.). km can fill that gap by defining a vault-native session format using the **same `org.acp.*` vocabulary** as #11, persisted as JSONL.

```
~vault/
  chats/
    refactor-extractbody-2026-04-27/
      session.jsonl        ← canonical event log (one event per line, org.acp.* schema)
      session.md           ← rendered markdown view (bidirectional, like km's notes ↔ tree)
      attachments/
        diff-001.patch
```

Each `.jsonl` line is an `org.acp.*` event with the same schema as the gateway's Matrix events. One vocabulary, two transports.

### The unification — one vocabulary on three transports

| Transport | What it looks like | Where it lives |
|---|---|---|
| Matrix room timeline | `org.acp.*` events as Matrix events | Element / Cinny / Slack-via-bridge |
| ACP gateway wire | `org.acp.*` events as JSON-RPC over UDS | runtime, in-memory |
| km vault | `org.acp.*` events as JSONL | on disk, durable, vault-native |

The same event sequence flows through all three. Implications:

- **km becomes the canonical session store** — Matrix rooms and ACP sessions both reduce to JSONL on disk.
- **Cross-agent portability is mechanical** — replay `session.jsonl` against any agent that accepts ACP context. Switch from Claude → Codex mid-session by re-feeding prompts.
- **The gateway becomes a tail** — `tail -f session.jsonl | mxc-publish` (or inverse for ingest). Gateway is essentially a transport-bridge.
- **Markdown round-trip extends naturally** — `session.md` is the human view, `session.jsonl` is machine source-of-truth. km already does this with notes ↔ tree.
- **Import is free** — Claude Code's existing `~/.claude/projects/*.jsonl` is *almost* the same shape; a small adapter ingests the entire history as historical chat rooms.

### Multi-agent comes for free at this layer (ACP can't do it)

ACP is strictly 1:1 — one client ↔ one agent over one stdio pair. There's no protocol-level concept of session participants, agent join/leave, or multi-agent routing.

But the room substrate (JSONL or Matrix) is **participant-aware by design**. So multi-agent works at this layer:

- Room owns the conversation; agents are stateless executors.
- Each agent maintains its own 1:1 ACP wire-session with the room manager.
- User prompt → room manager decides routing (broadcast / target / classifier) and feeds context to each agent's ACP session.
- Each agent emits responses; room manager tags with `agent_id`, appends to JSONL.
- Each agent reads room JSONL to "see" other agents (replayed as context on next prompt).

The spec ([`acp-event-spec.md`](../silvercode/future/ai-terminal/acp-event-spec.md)) gets two new event types — `org.acp.agent.join` and `org.acp.agent.leave` — and an `agent_id` field on every agent-emitted event. That's it. **The 1:1 ACP wire stays unchanged; multi-agent is purely a room-substrate feature.**

This is genuinely novel territory. Zed's multi-agent UX is "multiple sessions in tabs" (no shared room). LangGraph/AutoGen do multi-agent at framework level (Python code), not as persistent shared sessions. Nobody has shipped "shared room with N agents and N humans, persisted as a portable file format."

## What the prior-art map clarifies

1. **The architecture is validated** — Kong (~$2B), OpenRouter (~$1.3B), LangChain (~$1.25B) all prove the proxy-with-plugin-chain pattern reaches unicorn scale. Build with confidence.
2. **The protocol is the moat** — every adjacent product is HTTP-API-shaped (LLM gateways) or framework-shaped (LangGraph, CrewAI). ACP-shaped is open territory while ACP stays the standard.
3. **The cross-agent angle is the durable wedge** — Cursor ($50B), Anthropic, OpenAI, Sourcegraph all ship single-agent first-party. We can't beat them at single-agent; we can be the only player at cross-agent.
